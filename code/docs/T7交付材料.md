### 02 取消报名与自动递补时序图

实际调用路径为 [RegistrationRequestFilter](../src/main/java/edu/nju/workshop/registration/RegistrationRequestFilter.java) → [RegistrationController.cancel](../src/main/java/edu/nju/workshop/registration/RegistrationController.java) → [RegistrationService.cancel](../src/main/java/edu/nju/workshop/registration/RegistrationService.java) → [RegistrationRepository](../src/main/java/edu/nju/workshop/registration/RegistrationRepository.java)。

1. Filter 通过 `RegistrationAdmission.begin` 同时登记接收时间与在途请求；Controller 从 `AccountUser.current` 取得参与者身份。URL 同时携带场次与报名编号。
2. `cancel` 开启 READ_COMMITTED 事务，`lock` 用 `SELECT ... FOR UPDATE` 锁住场次，`owned` 在锁内核对参与者、场次、报名三者一致，再校验最新状态及截止资格。
3. `setStatus` 把本人记录改为已取消；若原记录为报名成功，`promote` 按 `waitlist_order, id` 读取队列，仅递补首位。退出候补不释放名额、不触发递补。
4. 取消、递补及 `logs.success` 共用事务；异常离开 `TransactionTemplate.execute` 后，由 `logs.failure` 的独立事务保存失败原因。
5. Filter 的 `finally` 调用 `RegistrationAdmission.end` 清除在途登记。截止任务确认没有截止前受理的请求后，才关闭剩余候补。

与原图的两处具体差别：实现先按请求中的场次编号加锁，再核对本人报名，无需在锁外反查场次；D-001 将图中的“锁内当前时间早于截止”改为“请求接收时间早于截止”，已经按时受理的取消及递补可以跨过截止时刻完成。场次是否结束仍按执行时刻判断。实体没有可变的 `cancelByParticipant/promote` 方法，状态由服务检查后直接写库，事务回滚撤销写入。

### 03 报名记录状态图

| 图中转换 | 实际入口与持久化方法 |
|---|---|
| 候补中 → 报名成功 | `RegistrationService.cancel/resize` 调用 `promote` → `RegistrationRepository.setStatus` |
| 候补中 → 候补未成功 | `RegistrationDeadlineJob.closeWaitlists` → `RegistrationService.closeDueWaitlists` → `RegistrationRepository.expire` |
| 候补中 → 已取消 | 本人 `RegistrationService.cancel`；场次联动 `cancelForSession` → `setStatus` |
| 报名成功 → 已签到 | [AttendanceService.checkIn](../src/main/java/edu/nju/workshop/attendance/AttendanceService.java) → `AttendanceRepository.checkIn`，保存首次签到时间 |
| 报名成功 → 缺席 | `AttendanceDeadlineJob.markAbsent` → `AttendanceService.markEndedAbsent/markAbsent` → `AttendanceRepository.markAbsent` |
| 报名成功 → 已取消 | 本人 `RegistrationService.cancel`；场次联动 `cancelForSession` → `setStatus` |
| 已签到 → 已取消 | `ActivityLifecycleService` 取消未结束场次 → `RegistrationService.cancelForSession` → `setStatus` |

合法新建由 `RegistrationService.apply` 和 `RegistrationRepository.insert` 完成。重复申请返回原非取消记录；已取消后重新申请建立新记录，重新候补使用历史最大顺序加一。状态枚举、数据库 CHECK 及服务校验共同约束状态；七条转换的测试方法见 [验收矩阵第 2 节](T7需求验收.md#2-req-006-七条转换)。截止处理采用上述 D-001 口径。

### 04 系统组件图

| 逻辑组件 | 实际类与位置 |
|---|---|
| 网站界面与请求入口 | [templates](../src/main/resources/templates/)、[static](../src/main/resources/static/)；各模块的 Controller；`SecurityConfig.securityFilterChain` 负责角色入口及 CSRF |
| 活动与场次 | `ActivityManagementService` 创建和初次审核；`PublishedActivityService` 处理发布后维护；`ActivityQueryService` 查询；[ActivityLifecycleService](../src/main/java/edu/nju/workshop/activity/ActivityLifecycleService.java) 取消活动或场次 |
| 报名与候补、签到与缺席 | `RegistrationService`、`RegistrationAdmission`、`AttendanceService`；两个 DeadlineJob 触发时间任务 |
| 名单与统计 | [StatisticsService](../src/main/java/edu/nju/workshop/statistics/StatisticsService.java) 的 `search/registrationsCsv/summaryCsv`；`StatisticsRepository` 汇总；`CsvWriter` 输出 CSV |
| 身份权限与操作日志 | `DatabaseUserDetailsService`、`AccountUser`；活动归属校验在 `ActivityManagementService`；管理查询范围统一由 `ManagementScopeService.resolve` 处理；`OperationLogService` 写日志，`OperationLogQueryService` 查询 |
| 持久化与事务 | 各 Repository 使用 JdbcTemplate；业务服务使用 `TransactionTemplate` 或 `@Transactional`；一个 Spring Boot 应用连接同一业务 MySQL 库 |

图中的 `ActivityService`、`AccessControl`、`TransactionSupport` 是逻辑职责，实际按上述类拆分。容量入口 `PublishedActivityService.resizeCapacity` 转交 `RegistrationService.resize`，由后者开启事务；取消活动则由 `ActivityLifecycleService` 开启事务，调用要求已有事务的 `cancelForSession`。报名服务通过 Repository 读取活动与场次，不反向调用活动服务。`StatisticsService` 使用只读 REPEATABLE_READ 事务，使列表、总数及统计来自同一已提交快照。
